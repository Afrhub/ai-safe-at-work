1. Scope, environment and conventions

1.1 In scope

  • Public marketing site, 50 root pages plus 29 templates, and every top navigation section.
  • Course, 11 core modules plus role tracks and sector overlays, quizzes, certificates.
  • Manager portal and Governance Centre, all 16 sections.
  • End user portal, progress, certificate, policy acknowledgement.
  • Reseller portal, deal registration, customers, commissions, marketing materials.
  • Authentication and authorisation, password, TOTP MFA, magic link, reset, RLS enforcement.
  • Payments, Stripe Bacs Direct Debit checkout and the fulfilment webhook.
  • Cross cutting, CSP, caching, SEO and robots posture, accessibility, responsive layout.

1.2 Out of scope

  • Supabase, Netlify and Stripe platform internals. We test our use of them, not the vendors.
  • Video rendering pipeline in video-project/, which is not deployed.
  • Internal slide decks, which are known to be broken live by CSP and are parked deliberately.

1.4 Conventions

Every case carries an ID, the steps, and an expected result stated in observable terms. A case passes only when the expected result is observed in full. Partial matches fail.

PriorityMeaning
P1Blocks release. Money, access control, data loss, or a broken primary journey.
P2Significant defect. A journey works but is degraded, or a secondary feature is broken.
P3Cosmetic, copy, or nice to have. Log it, do not block on it.
Read section 11 before running anything. Four known platform states will make large parts of this plan fail for reasons that are not defects in the code under test. Sections F, G and the manager and end user flows are all affected. Record those as Blocked, not Failed.

2. Section A, end to end user flow scenarios

Each flow is a single continuous journey. A flow fails at the first step whose expected result is not met. Run flows before the functional sections, they surface integration defects that per screen testing hides.

A1, Prospect discovers, evaluates and buys Foundation

Playwright is not installed in this repository by design. The dashboard tests borrow it from a sibling project via createRequire, which has broken once already. Reinstall it in a scratch directory or expect those two to fail for environmental reasons.

10.2 Recommended automation order

  1. Section G and the RLS block. Money and access control, cheap to assert, catastrophic to get wrong. Mostly automatable without a browser.
  2. EXP-01 to EXP-05. A handful of curl calls checking status codes. Should run on every deploy, because Netlify publishes the whole repository.
  3. Flows A1 and A3. The two journeys that earn and deliver.
  4. Section C. Highest surface area, slowest to automate, best value from the existing Playwright suite.

10.3 Entry and exit

Entry A deploy is green, the four blockers in section 11 are either resolved or explicitly accepted as Blocked, and test accounts exist for all three roles.

Exit Every P1 passes or has a written, accepted waiver. No P1 defect is open. Every P2 is triaged. Flows A1 to A5 complete end to end without a workaround.
